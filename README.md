# vaibes

My personal library of agent skills, and the agent setup that goes with them.

## Install

```bash
npx skills@latest add ronalson/vaibes
```

> See https://github.com/vercel-labs/skills for more options.

`npx skills` installs only `skills/`. For the agent rules, role files, and `agent-role`, see [Agent setup](#agent-setup).

## Agent setup

`install.py` puts the global agent rules, the read-only role rules, the Claude agent files, and the `agent-role` launcher into your home directory. It needs Python 3.9 or later and nothing outside the standard library. It reads nothing from the network or the environment except the home directory.

| Folder | Holds |
| --- | --- |
| `rules/` | `global.md`, the shared rules, and `delegation.md`, the delegation section. |
| `roles/` | Tool-neutral rules for the read-only `scout` and `reviewer` roles, used by Grok and Pi. |
| `claude-agents/` | The Claude `scout` and `worker` agent files. |
| `bin/` | `agent-role`, which starts a read-only role in Claude, Grok, or Pi. |

| Source | Target | When |
| --- | --- | --- |
| `bin/agent-role` | `~/.local/bin/agent-role` (mode 0755) | any agent |
| `roles/scout.md`, `roles/reviewer.md` | `~/.config/agent-roles/` | any agent |
| `claude-agents/scout.md`, `claude-agents/worker.md` | `~/.claude/agents/` | `claude` |
| `rules/global.md` + `rules/delegation.md` | managed block in `~/.claude/CLAUDE.md` | `claude` |
| `rules/global.md` + `rules/delegation.md` | managed block in `~/.codex/AGENTS.md` | `codex` |
| `rules/global.md` + `rules/delegation.md` | managed block in `~/.grok/AGENTS.md` | `grok` |
| `rules/global.md` only | managed block in `~/.pi/agent/AGENTS.md` | `pi` |

### Usage

Name the agents the machine uses. On a laptop with Claude Code, Codex, and Pi:

```bash
python3 install.py claude codex pi
```

On a server with Claude Code and Grok:

```bash
python3 install.py claude grok
```

Run it again after pulling to apply new rules. `~/.local/bin` must be on your `PATH` for `agent-role`.

`--check` writes nothing. It prints one status line per target and exits 0 only when every target is `ok`:

| Status | Meaning |
| --- | --- |
| `ok` | The target matches the repository. |
| `missing` | The file, or its rules block, does not exist yet. |
| `outdated` | The target is unchanged since the last install and the repository has newer content. |
| `changed locally` | The target was edited after the last install, or exists but was not installed by vaibes. |
| `symlink` | The target, or a folder above it inside the home directory, is a symlink. |
| `bad markers` | The startup file has a broken rules block. |

```bash
python3 install.py --check claude codex pi
```

### Managed block

Startup files such as `~/.claude/CLAUDE.md` can hold text that belongs to the machine, such as an import of a machine guide. The installer only owns the text between these two lines:

```text
<!-- BEGIN vaibes rules: generated by vaibes install.py; edit rules/ in the vaibes repository -->
...rules...
<!-- END vaibes rules -->
```

- A missing file is created with only the block.
- A file without markers gets a blank line and the block appended at the end.
- A file with one BEGIN line followed by one END line has the text between them replaced.
- Any other marker layout is refused.

Text outside the block is never changed. To change the rules, edit `rules/` here and install again; edits inside the block are treated as local changes.

### Refusals

`~/.config/vaibes/install-state.json` records the SHA-256 of each file, and of each block's contents, that the installer last wrote. A target is written only when it is missing, already matches, or still matches the recorded hash. The installer refuses a target when:

- it is a symlink, or sits inside a symlinked folder, such as a leftover stow link. Unstow the old package first, for example `./install.sh --delete agents` in dotfiles;
- it was changed since the last install;
- it exists but was not installed by vaibes;
- its rules block markers are malformed.

The installer checks every target before it writes anything. If any target is refused, it writes nothing and exits 1. Move your local changes into the repository, or delete or rename the target, then run it again. Each write goes to a temporary file in the same folder and then replaces the target.

### Removing

The installer never deletes files, including when you drop an agent from the list. To remove the setup by hand:

1. Delete the copied files: `~/.local/bin/agent-role`, `~/.config/agent-roles/scout.md`, `~/.config/agent-roles/reviewer.md`, `~/.claude/agents/scout.md`, and `~/.claude/agents/worker.md`.
2. In each startup file from the targets table, delete the lines from `<!-- BEGIN vaibes rules` through `<!-- END vaibes rules -->`, and the blank line the installer added before them. Delete the file if nothing else is left.
3. If you removed everything, delete `~/.config/vaibes/install-state.json`. When you remove only some targets, keep it: entries for removed targets do no harm, and the remaining targets need theirs to accept updates.

## Skills

| Skill | Use For | Not For |
| --- | --- | --- |
| [`breakdown`](./skills/breakdown/SKILL.md) | Step 2 of spec → breakdown → delegate → review: splitting a settled spec or plan into vertical, reviewable phases that agents can run in order or in parallel. | Breaking down a plan the user has not agreed to, or horizontal layering. |
| [`bro`](./skills/bro/SKILL.md) | Restating the previous message in plain, concise language. | Providing new analysis, instructions, or technical detail. |
| [`codebase-design`](./skills/codebase-design/SKILL.md) | Designing deep modules, improving interfaces, finding seams, and making code easier to test or navigate. | General implementation work that does not involve module or interface design. |
| [`create-verification-skill`](./skills/create-verification-skill/SKILL.md) | Generating a project-local `verify-<app>` skill in `.claude/skills/` that launches the real app, drives features the way a user does, and captures evidence. | Unit tests, CI setup, or repos that already have a working verify skill. |
| [`delegate`](./skills/delegate/SKILL.md) | Step 3 of spec → breakdown → delegate → review: executing a spec's `## Phases` in herdr, with workers in their own worktree workspaces, wave by wave, with result files, `verify-<app>` evidence, an integration merge, and a cleanup sweep. | Planning or writing specs (use `handoff`, `type-spec`, `breakdown`), reviewing the result (use `review`), or running outside herdr. |
| [`deslop`](./skills/deslop/SKILL.md) | Reviewing a branch diff against a requested or discovered base to remove AI-generated code slop while preserving behavior. | Broad refactors, intentional behavior changes, or solving unclear bugs. |
| [`file-pr`](./skills/file-pr/SKILL.md) | Opening a pull request or updating an existing one within the request, with a clear title and concise body. | Making commits, pushes, or implementation changes. |
| [`grill-me`](./skills/grill-me/SKILL.md) | Relentlessly stress-testing a plan, decision, or idea through structured questions. | Implementation or lightweight brainstorming that does not need a decision audit. |
| [`handoff`](./skills/handoff/SKILL.md) | Step 1 of spec → breakdown → delegate → review for work too large for one prompt: handing planned work to another agent or a fresh session as a short implementation spec in `context/specs/`, with a required Validation section tied to the repo's `verify-<app>` skill. | Typed architecture specs (use `type-spec`) or small work a single prompt can hold. |
| [`html-doc`](./skills/html-doc/SKILL.md) | Creating a single-file HTML document for specs, findings, reports, comparisons, and visualizations. Its CDN styling requires network access. | Plain-text answers or documents that must use another file format. |
| [`maintain-verification-skill`](./skills/maintain-verification-skill/SKILL.md) | Auditing an existing `verify-<app>` skill and its feature map against the source and a live session, then fixing proven drift. | Creating a verify skill from scratch or changing app behavior. |
| [`prototype`](./skills/prototype/SKILL.md) | Building a throwaway prototype to explore a state model, business logic question, or UI direction before committing to it. | Production implementation, polished UI delivery, persistent data flows, or long-lived experiments. |
| [`review`](./skills/review/SKILL.md) | Step 4 of spec → breakdown → delegate → review: reviewing `<base>..<head>` with a read-only reviewer from another model family in herdr, confirming or rejecting each finding against the code and the spec's Validation evidence, and giving a merge or fix verdict. | Fixing the findings (use `delegate` or a worker) or running outside herdr. |
| [`show-me`](./skills/show-me/SKILL.md) | Explaining the current topic with concise diagrams, code-shape sketches, and focused HTML artifacts. | Long prose lessons or visuals that do not answer the current question. |
| [`tdd`](./skills/tdd/SKILL.md) | Building features or fixing bugs with a red-green-refactor loop and behavior-focused tests. | Bulk test generation, implementation-detail tests, or changes where tests are intentionally out of scope. |
| [`teach-codebase`](./skills/teach-codebase/SKILL.md) | Explaining a codebase, subsystem, runtime path, or symbol so someone can change it safely. | Implementing changes or giving ungrounded architectural advice. |
| [`technical-writing`](./skills/technical-writing/SKILL.md) | Writing or reviewing clear technical docs, RFCs, READMEs, PR descriptions, and commit messages. | Product UI copy or documentation outside the project's real terminology and behavior. |
| [`type-spec`](./skills/type-spec/SKILL.md) | Step 1 of spec → breakdown → delegate → review when the design needs it: a typed call-stack architecture spec with typed contracts and execution flows. Design only. | Smaller specs (use `handoff`), implementing the design, or inventing requirements without enough context. |
| [`unslop`](./skills/unslop/SKILL.md) | Editing writing to remove AI tells and give it a specific, human voice. | Changing the underlying meaning, facts, or intended tone. |
