# Technical writing

Write technical material that a tired engineer can understand on the first read. Preserve the requested facts, scope, terminology, quotations, code, and uncertainty. Do not alter another skill or repository policy as part of ordinary writing work.

## Choose the document shape

Match the structure to the artifact and reader. Use a tutorial for guided learning, a how-to for a bounded task, reference for lookup, and explanation for a bounded why question. Split or link material only when mixing modes would make it harder to use. Do not force a template on a short answer, README, RFC, PR description, or commit message.

## Write with precision

- Use the repository's real names for symbols, paths, flags, commands, and concepts.
- State who does what. Put conditions before the action they affect.
- Prefer direct words and direct verbs. Cut filler without removing a necessary qualification.
- Keep instructions actionable, facts distinct from rationale, and uncertain claims visibly qualified.
- Follow the project's established Markdown, code-block, and indentation conventions.
- Use headings and lists when they improve scanning. Keep a logical hierarchy and use descriptive link text.

For detailed sentence, ambiguity, and document-mode guidance, read [style-layers.md](references/style-layers.md) only when the request needs it.

## Review and completion

Before delivering, verify that the text preserves technical meaning, uses project terms consistently, and fits the requested artifact. Check stated paths, symbols, counts, commands, and citations against the available evidence. Finish with the requested writing or review; do not create follow-up edits unless the user asks.
